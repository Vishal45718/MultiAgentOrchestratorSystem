|---|---|---|---|---|
| D001 | init | LangGraph for orchestration | Explicit state graph, native checkpointing, fits multi-agent + HITL resume needs | Plain function-calling loop, CrewAI |
| D002 | init | PostgreSQL as sole system of record | Durable, relational, queryable audit trail; single source of truth | Store state only in Redis (rejected: not durable) |

| D006 | 2026-09-16 | SQLAlchemy 2.0 Declarative Models with Dialect-Agnostic Types | Use SQLAlchemy 2.0 `DeclarativeBase`, `Mapped[...]`, `Uuid` primary keys, `JSON().with_variant(JSONB, 'postgresql')`, and `native_enum=False`. Ensures type safety, full PostgreSQL optimization in production, and effortless in-memory SQLite unit testing without Docker requirements. | Integer auto-increment IDs, pure PostgreSQL-only types without dialect fallback, native Postgres enums. |
| D007 | 2026-09-16 | Alembic env.py reads DATABASE_URL from src.config settings at runtime | Prevents hard-coding credentials in alembic.ini. `env.py` imports `settings.sync_database_url` dynamically; `alembic.ini` sets `sqlalchemy.url = placeholder` which env.py overrides. Migration file is hand-reviewed after autogenerate to ensure correctness. psycopg2-binary added as dev dependency for migration execution only; production will use the real driver pinned in Dockerfile. | Storing DATABASE_URL directly in alembic.ini (insecure), using `%` interpolation from env file (fragile). |

| D008 | 2026-09-16 | Repository layer uses PostgreSQL for integration tests (not SQLite) | Schema uses PostgreSQL-native types (JSONB, dialect-specific UUID, non-native enums). SQLite cannot exercise the same JSON/JSONB column behavior or enum string enforcement. Integration tests run against the existing Docker Postgres 15 service with a dedicated `test_orchestrator` database. Unit-level behavior (Python-level object creation, repr, field defaults) remains in the existing SQLite-backed model tests. Repository tests use a real Postgres session, real transactions, and explicit rollback-based isolation per test. No new `testcontainers` dependency is introduced; the existing docker-compose Postgres service is used. | Use SQLite for all tests (rejected: JSONB/enum behavior differs); introduce testcontainers (rejected: adds new dependency not called for by task). |
| D009 | 2026-09-16 | Repositories accept `Session` directly (no implicit session management) | Repositories take an injected `sqlalchemy.orm.Session` and never call `session.commit()` — callers control transaction boundaries. This ensures multi-step operations across repositories can be wrapped in a single transaction by the service/orchestration layer (Phases 4–7). `NotFoundError` is a typed exception raised on `get_by_id` misses, not a silent `None` return. | Auto-commit sessions (rejected: breaks multi-repo transactions); return `None` on not-found (rejected: forces caller to handle None vs missing distinction). |

| D010 | 2026-09-17 | Use standard Python dataclass for ToolDefinition | `ToolDefinition` uses `dataclasses.dataclass` with explicit `validate()` method rather than Pydantic because Pydantic does not smoothly serialize arbitrary Callables out-of-the-box without workarounds, and standard Python validation is lightweight, model-agnostic, and sufficient for the registry. | Pydantic BaseModel (rejected: callable validation is complex). |
| D011 | 2026-09-17 | Define minimalist provider-neutral JSON schemas | The schemas are defined as plain JSON files with `name`, `description`, and `input_schema`. They are strictly mapped to JSON schema specs without provider-specific cruft (e.g., no strict `strict` flags or Anthropic XML tags). `additionalProperties: false` is enforced for strict inputs. | Hardcoding schemas as python dicts in code (rejected: harder to validate and share across platforms). |
| D012 | 2026-09-17 | OpenAI function-calling adapter via pure translation layer | Implement pure adapter in `src/tools/openai_adapter.py` mapping canonical `ToolDefinition` to OpenAI tool specification `{"type": "function", "function": {"name": ..., "description": ..., "parameters": ...}}`. Validates ToolDefinition and OpenAI constraints (64-char name limit, object schema), uses deepcopy to prevent schema mutation leaks, supports optional `strict` flag without requiring the external `openai` SDK dependency. | Add `openai` SDK dependency (rejected: unnecessary dependency for schema translation); mutate canonical schemas in-place (rejected: breaks provider neutrality). |
| D013 | 2026-09-17 | Anthropic tool-use adapter via pure translation layer | Implement pure adapter in `src/tools/anthropic_adapter.py` mapping canonical `ToolDefinition` to Anthropic tool specification `{"name": ..., "description": ..., "input_schema": ...}`. Validates ToolDefinition and Anthropic constraints (64-char name limit, object schema), deepcopies input schema for isolation, and achieves complete semantic parity with OpenAI adapter while keeping canonical definitions model-agnostic. | Add `anthropic` SDK dependency (rejected: unnecessary dependency for schema transformation); modify canonical schemas to Anthropic-specific formatting (rejected: breaks provider neutrality). |
| D014 | 2026-09-17 | Pluggable KB backend protocol and stateless default tool registry loader | Define `KBBackend` Protocol with `InMemoryKBBackend` default for `kb_retrieval_tool` to allow fast, deterministic unit testing without external ChromaDB dependencies in Phase 3, while preserving a clean migration path to ChromaDB in Phase 5. Implement `create_default_tool_registry()` in `src/tools/loader.py` to load canonical JSON schemas directly from disk and avoid global mutable registry state. | Hardcode document search in tool function (rejected: requires refactoring for ChromaDB); store global singleton registry (rejected: introduces state pollution). |
